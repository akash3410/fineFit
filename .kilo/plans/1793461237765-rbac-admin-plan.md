# RBAC Admin System Implementation Plan

## 1. Reusable Existing Components
- `apps.accounts.CustomUser` already has `email`, `phone_number`, `groups`, `user_permissions`, `is_staff`, `is_superuser`.
- Django auth Groups/Permissions already wired; reuse as roles/permissions instead of duplicate models.
- `apps.admin_panel` already provides staff-only CRUD views and sidebar.
- `staff_required` decorator already gates admin panel.

## 2. Recommended Architecture
Use Django's built-in Groups as Roles and Permissions as granular capabilities. Add a thin `Role` proxy? No. Use Group directly with admin UI. Custom role = Group. Permission assignment = group.permissions. Admin users = CustomUser with is_staff=True and groups. Superuser bypasses checks.

Backend enforcement via Django permissions (codenames) and custom permission classes/decorators. Frontend hides menus based on `/api/v1/me/` permissions but backend remains authority.

## 3. Database / Models
No new core models required initially. Optional:
- Add `display_name`? first_name/last_name already.
- Add `last_login` exists.
- Add `is_active` exists.
Potential `Role` metadata not needed; Group has name. If descriptions needed, create `RoleProfile` (OneToOne Group) later. Keep out of scope to avoid duplication.

Permissions: use Django's Permission objects. Custom permissions on catalog models or app-level permissions. Define permissions for modules: view/add/change/delete products, categories, etc. plus dashboard, orders, customers. Use Django's default model permissions plus custom `manage_orders`, `manage_customers`, `access_dashboard`.

## 4. Authentication Strategy
- Extend `SessionLoginView` to accept `identifier` (email or phone) and password. Lookup user by email (case-insensitive) or phone_number. Keep existing email flow for compatibility.
- Phone login requires unique phone numbers; enforce unique constraint (nullable) or validate uniqueness in admin creation.
- Admin creation form includes name, email, phone, password, role(s). Set is_staff=True. Hash password via set_password.

## 5. Role & Permission Management
- Superuser-only views under admin panel:
  - `/admin/admins/` list/create/edit/delete admin users
  - `/admin/roles/` list/create/edit/delete roles (Groups) and assign permissions
- Permission catalog endpoint: list available permissions grouped by app/model.
- Assign roles to admin users; optionally direct permissions (prefer group only).
- Prevent privilege escalation: non-superuser cannot create/edit superuser or assign permissions they lack; backend validates.

## 6. Backend APIs / Views
- Admin user CRUD views (staff + superuser required).
- Role CRUD views (superuser required).
- Permission list view (superuser).
- Permission enforcement: replace `staff_required` with `permission_required`-based checks per view or custom decorator `admin_permission_required(perm)`.
- Add decorators to each admin_panel view mapping to permissions:
  - dashboard: `access_dashboard` or staff
  - categories: view/add/change/delete_category
  - products: etc.
- Expose permissions in `CurrentUserView` serializer for frontend.

## 7. Frontend / Sidebar
- Add sidebar entries: Admins, Roles & Permissions (superuser only).
- Conditionally render based on permissions.
- Admin user management pages and role management pages.
- Admin login supports email/phone.

## 8. Security
- Backend is authority; frontend hiding only UX.
- Superuser-only for role/admin management.
- Prevent self-deletion/demotion of last superuser.
- Validate role assignment subset of requester's permissions.
- Use CSRF, session auth.
- Audit logging optional.

## 9. Files to Create/Modify
Create:
- `apps/accounts/authentication.py` (identifier backend)
- `apps/admin_panel/role_views.py` or extend views
- templates: `admin_panel/admins/*`, `admin_panel/roles/*`
- frontend pages/components for admins/roles
Modify:
- `apps/accounts/views.py`, serializers, urls
- `apps/admin_panel/views.py`, urls, sidebar
- `config/settings/base.py` (AUTHENTICATION_BACKENDS)
- permissions definitions in models/admin or migrations
- frontend api/types/routes/navbar

## 10. Implementation Order
1. Add phone uniqueness + custom auth backend.
2. Define custom permissions (migrations).
3. Add permission enforcement decorators and map views.
4. Add admin user CRUD.
5. Add role CRUD + permission assignment.
6. Update sidebar + frontend pages.
7. Tests for auth, permissions, escalation.
8. Migrations and validation.

## 11. Validation
- Non-staff cannot access.
- Role without product permission cannot access product views.
- Superuser full access.
- Phone login works.
- Escalation attempts blocked.
